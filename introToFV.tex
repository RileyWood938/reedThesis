\subsection{The Abstraction Function}

As we saw in the previous example, the ``abstraction function" $\alpha$ is critical for providing additional reasoning capabilities to the computer.
In general, $\alpha$ is thought of as taking program variables and giving us an element in some ``Abstract Domain".
What we hope is that the elements in our domain will in some way be an overapproximation of the actual values. 
In our example, this domain consisted of possible combinations of $-, 0,$ and $+$, and it is easy to see how we get an overapproximation from this choice.
If $x$ could be positive, we have $\alpha(x)$ contain ``$+$", which represents all positive numbers, surely a good approximation for any particular positive number.

To make this notion of overapproximation formal, it is first useful to introduce the opposite operation, a concretization fucntion $\gamma$. 
This function takes something in the abstract domain and tells us what ``real values'' it could have. 
In our example above, we could consider
\[
\gamma(\{0\}) = \{0\} \mand \gamma(\{+\}) = \{1, 2, 3, \ldots \}.
\]
With $\gamma$ in hand we can describe the idea of overapproximation as follows:
\[
x \subseteq \gamma(\alpha(x))
\]
That is, if we take $x$ and abstract it, then the concrete values which $\alpha(x)$ could take should include the actual value of $x$.

The other desired effect of $\alpha$ is to take some operation like $+$ and give us a version which works on elements of the abstract domain.
If we let $c$ represent some statement in the program, we are interested in an abstract version of that statement $\llbracket c \rrbracket$.
The idea is that given some program state, we can apply $c$ to get to another program state.

\subsection{Abstract Domains}

With the work of $\alpha$ clarified, we move our discussion to where alpha takes our program variables to.
The abstract domain is where our approximations of variables live, and the example of sign analysis uses subsets of $\{-, 0, +\}$ as our abstract domain.
It is clear that this domain gives us an overapproximation that is correct, but we may run into situations where this domain overapproximates too much for us to prove any useful properties.
Consider the following program
\begin{code}
Assert x >=2
if x == 1:
  kill
\end{code}
In this program it is clearly impossible for \kil to be reached, but
\[\alpha(x) = \{+\}\mso 1 \in \gamma(\alpha(x)).\]
Thus the check \codex{x == 1} could appear true because our abstract domain thinks that $1$ is a possible value of $x$.
The problem here is that our domain is only able to record that $x$ is positive, so that the information $x >=2 $ is approximated by $x > 0$.
This program would then fail to be verified by sign analysis.

In this case, we can resolve the issue by moving to a more expressive domain.
Rather than considering only the sign of $x$, we can let $\alpha$ give us an upper and lower bound on the values of $x$.
In this case, 
\[
  \alpha(x) = [2, \inf]
\]

This domain allows us to see that
\[
  \gamma(\alpha(x)) = \gamma([2, \inf]) = \{2, 3, \ldots\}
\]
which does not contain $1$.
This allows us to verify that $\kil$ is never reached.

This has demonstrated how our choice of abstract domain can change which programs will pass verification.
With a more expressive domain, we get a finer overapproximation, and hence more programs will be verifiable.
Coupled with this is an increased computational cost associated with more expressive domains. 
In the case of intervals, we are now keeping track of two bounds per variable, and computations $\llbracket c \rrbracket$ must take both bounds into account.

We distinguish one state $\w_{\init}$ as the starting configuration of the program.
This state must have location $\ell_0$, the first label in the code, and will map all variables to the set of possible valuations at the start of execution.
It is worth noting that there are a potentially infinite family of initial states.
For example if we begin the program with \codex{x} assigned to $0$ or $1$, then there is an initial state with $\w(x) = \{0, 1\}$ but also $\w(x) = \{0, 1, 2\}$ and so on.

To resolve this we choose $\w_\init$ to be the least upper bound of all initial configurations.

For some subset of our code $c$, we might be interested in what states we can get to by running $c$.
We write $\w \llb c \rrb \nu$ to denote that we can run $c$ starting in state $\w$ and it will terminate in state $\nu$.
This only makes sense if the start location of the code $c$ is compatible with $\w$'s associated location. 
For this triple $\w \llb c\rrb v$ to be valid, we require $\ell(\w)$ to equal the start location of $c$.

Then we can abstract the initial state, and begin stepping through the code, checking after each line to see if our abstract state overapproximates any concrete error states.

\section{Abstract Transformers}

Remaining is the challenge of picking a suitable abstract lattice, and defining the abstract semantics for certain commands $\llb c \rrb ^\#$.
We shall tackle the second issue, and defer abstract lattices to a later chapter.

We have seen examples in the interval domain where the abstract semantics of adding $1$ to a variable increases both endpoints of our abstract element.
In general, intervals are quite good for capturing mathematical operations of this sort, as we have a relatively easy time programming how operations like multiplication, addition, and subtraction will affect a range of possible values.
Consider, however, the following program:
\begin{code}
  Assert 0 < x < 5
  if (x == 1):
    x = 10
  else:
    x = -x
\end{code}
This code begins with $\alpha(x) = [1, 4]$, an abstraction which intervals capture quite tightly, but then we encounter a control flow concept.
In order to find the possible values of $x$ after this \codex{if} statement, we must follow all paths that the program could take. 
This requires us to split into two interpretations, one for the branch \codex{x=10} and one for \codex{x = -x}.

To do this formally, if may be useful to think of defining a transformer for a general if statement of the form \codex{if c: x else: y}, where \codex{x} and \codex{y} are parts of the program. 
We can then think about splitting up our program into two branches.
The \codex{if} branch should start in the initial state $\w$ subject to the condition that $c$ is true, and then perform interpretation of \codex{x}.
The starting state subject to the condition that $c$ is true can be denoted $\w \meet c$ where $c$ captures the least upper bound of states that make $c$ true.
We can notate this as
\[(\w \meet c)\llb \codex{x} \rrb\nu \]
To say that the first branch lands us in state $\nu$.
Similarly for the else branch we get 
\[(\w \meet !c)\llb \codex{x} \rrb\nu \]
\[\w \llb \codex{if c: x else: y} \rrb = (\w \meet c)\llb \codex{x} \rrb \join (\w \meet !c) \llb \codex{y} \rrb \]

Following the first branch takes us to $\ell_4$, where we know that $x$ can only be $1$.
The conditional can be satisfied, as $1 \in [1, 4]$, so we can follow this branch, but while doing so we can narrow our abstraction so that $x$ is in the interval $[1]$.
Now we can apply the semantics of line $3$ to get $x$ in $[10]$.

Similarly for the \codex{else} path, the conditional narrows our interval to $[2, 4]$, and then the semantics of line $5$ tell us that $\alpha(x) = [-4, -2]$.

But now we have a problem, after this control flow ends we reach $\ell_7$ where the two paths must recombine, but their intervals are not compatible.
We know that $x$ lives in one of $[-4, -2]$ or $[10]$ but not which one.
To continue with just $1$ case to check, we must find a new overapproximation of these two intervals.
This requires us to compute the join in $L_a$, in this case $[-4, -2] \sqcup [10] = [-4, 10]$.
Now we once again have a single overapproximation, but it has become a far less accurate approximation of the actual values of $x$.
Control flow operations almost always require us to compute the join of our abstract elements, frequently to the detriment of our approximation's quality.

Another challenge we face when performing abstract interpretation is loops.

  while (x<1):
    x = x+1 
\end{code}
